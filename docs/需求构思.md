# 学生宿舍报修管理系统 —— 项目需求构思

> 课程：软件工程（吕云翔《软件工程——理论与实践》第三版）
> 项目类型：小型信息系统 · 个人独立完成
> 技术：Python + Django + MySQL

---

## 一、项目背景

**现状痛点**

1. 学生报修多靠口头、电话或楼栋群发消息，信息零散，容易被聊天记录刷掉。
2. 报修后没有回执，学生不知道是否被受理、维修人员何时上门。
3. 纸质登记难以统计和追溯，重复报修与漏单无人发现。

问题的本质：报修信息没有结构化载体，处理过程没有状态流转，处理结果没有数据沉淀。

**建设目标**

构建一个在线报修系统，实现"报修—派单—维修—验收—归档"的业务闭环：学生在线提交报修并随时查看进度，宿管集中受理与派单，维修人员接单并记录维修过程，管理者获得报修量、完成率、故障分类等统计数据。

**可行性**：业务本质是表单录入 + 状态流转 + 列表查询，无高并发和复杂算法；单校区规模（数千学生、年均约 2 万条工单）用单机 MySQL 即可承载；技术栈全部开源，零成本，个人在一个学期内可完成。

---

## 二、技术选型

| 层次 | 技术 | 说明 |
| --- | --- | --- |
| 开发语言 | Python 3.10+ | 语法简洁，个人开发效率高 |
| 后端框架 | Django 5.2 LTS | 自带 ORM、认证、表单与后台管理，可省去大量基础代码；5.2 与 MySQL 8.0 兼容 |
| 数据库 | MySQL 8.0 | 课程要求；使用 mysqlclient 驱动连接 |
| 前端 | Django 模板 + Bootstrap 5 | 服务端渲染，免去前后端分离与接口联调；响应式适配手机 |
| 图片上传 | ImageField + Pillow | 支持报修现场照片与完工照片 |
| 权限控制 | Django 内置认证 + 自定义角色字段 | 用一个用户表区分三个角色 |
| 后台管理 | Django Admin | 承担报修分类、楼栋房间、用户等基础数据维护 |
| 统计图表 | ECharts（可选） | 报表可视化，作为后期增强 |
| 开发工具 | PyCharm 或 VS Code、Navicat、Git | 编码、数据库管理、版本控制 |
| 运行部署 | 开发期 `runserver` 演示 | 单机运行，满足课内验收 |

> 关键取舍：不做前后端分离。服务端渲染加内置认证能显著降低个人开发量，把时间留给需求分析、状态流转与测试，也更符合课程看重工程过程完整性的评分取向。

## 三、系统架构

采用 Django 默认的 **MVT（Model–View–Template）单体架构**：

```
浏览器（学生 / 维修人员 / 宿管）
        │ HTTP 请求
        ▼
URL 路由 ──► 装饰器（登录校验 + 角色校验）
        ▼
视图 View（业务逻辑、工单状态流转、权限判断）
   ├── Model（Django ORM）──► MySQL 8.0
   └── Template（Django 模板 + Bootstrap 5）
        ▼
返回 HTML 页面
```

| 层次 | 职责 |
| --- | --- |
| Model | 定义数据模型，通过 ORM 操作数据库，管理图片上传路径 |
| View | 处理请求与业务规则，是工单状态流转的唯一入口 |
| Template | 页面展示，按角色渲染不同菜单与操作按钮 |
| 路由与装饰器 | URL 映射，统一做登录与角色权限拦截 |

**部署**：单机部署，Django 开发服务器 + MySQL 即可完成演示验收；图片保存到项目 `media/` 目录，数据库中只存相对路径。

## 四、角色与权限

系统只设三个角色，共用一个用户表，以角色字段区分：

| 角色 | 主要权限 |
| --- | --- |
| 学生 | 提交报修、可选上传照片、查看与撤销自己的工单、验收与评价 |
| 维修人员 | 查看分派给自己的任务、接单、更新维修进度、填写维修记录、提交完工 |
| 宿管/管理员 | 查看全部工单、受理与驳回、派单与改派、基础数据维护、统计报表 |

权限实现：学生只能访问自己的工单，维修人员只能访问分派给自己的工单，宿管可访问全部。校验统一在视图层完成，防止通过修改 URL 越权访问。

## 五、功能概述

个人项目，共设 4 个功能模块。课程要求"每人独立完成至少两个功能模块"，本方案由本人全部完成，满足要求。

| 模块 | 面向角色 | 功能要点 |
| --- | --- | --- |
| M1 用户认证与个人信息 | 全部 | 注册、登录、退出、修改密码、个人信息与所属楼栋房间维护 |
| M2 报修管理 | 学生 | 提交报修（填写楼栋房间、分类、描述、紧急程度，可选上传照片）、我的报修列表与进度时间线、撤销报修、验收与评分评价 |
| M3 维修处理 | 维修人员 | 我的任务列表、接单、更新状态、填写维修记录（故障原因/处理措施/更换材料）、上传完工照片、提交完工 |
| M4 管理端 | 宿管/管理员 | 工单池筛选与受理/驳回、派单与改派、超时未受理提醒、报修分类与楼栋房间维护、统计报表（报修总量、分类占比、完成率、人员工作量） |

其中 M4 的基础数据维护可直接由 Django Admin 承担，进一步压缩开发工作量。

## 六、核心业务流程

**主流程**

1. 学生登录 → 填写报修信息（可选附现场照片）→ 提交，系统生成工单号，状态为"待受理"。
2. 宿管在工单池查看 → 受理并指派维修人员（或填写原因驳回）。
3. 维修人员接单 → 上门维修 → 更新进度、填写维修记录 → 提交完工。
4. 学生验收：通过则评分评价，工单完成；未修复则填写原因，退回重新派单。
5. 工单归档，数据计入统计报表。

**工单状态机**

| 状态 | 含义 | 可流转到 | 触发者 |
| --- | --- | --- | --- |
| 待受理 | 已提交，尚未受理 | 已派单、已驳回、已撤销 | 宿管 / 学生 |
| 已派单 | 已指定维修人员 | 维修中、已派单（改派） | 维修人员 / 宿管 |
| 维修中 | 已接单，处理中 | 待验收 | 维修人员 |
| 待验收 | 维修完成，等待确认 | 已完成、已派单（退回重派） | 学生 |
| 已完成 | 验收通过并归档 | — | 学生 |
| 已驳回 | 不受理（非职责范围、重复报修等） | — | 宿管 |
| 已撤销 | 受理前学生主动撤销 | — | 学生 |

状态流转只在视图层校验，禁止页面直接修改状态字段。这是系统最核心的业务规则，也是测试用例设计的重点。

**异常处理**：同一楼栋房间与同一分类存在未完成工单时提示重复报修；超过设定时长仍未受理的工单在管理端标记为超时；验收未通过时记录退回次数。

## 七、数据模型概要

| 模型 | 说明 | 主要字段 |
| --- | --- | --- |
| User | 用户（继承 Django 内置用户模型） | 学号/工号、姓名、密码、手机号、角色、楼栋房间 |
| Building / Room | 楼栋与房间 | 楼栋名、房间号、楼层 |
| RepairCategory | 报修分类 | 分类名（水电/家具/门窗/网络/其他）、默认工种 |
| RepairOrder | **报修工单主表** | 工单号、报修人、楼栋房间、分类、故障描述、紧急程度、状态、维修人、各节点时间、驳回原因、验收结果、评分 |
| OrderImage | 工单图片 | 关联工单、图片路径、类型（报修/完工） |
| RepairRecord | 维修过程记录 | 关联工单、操作人、操作类型、说明、时间 |
| Evaluation | 验收评价 | 关联工单、是否修复、评分、评价内容 |
| OperationLog | 操作日志（可选） | 操作人、操作模块、操作内容、时间 |

设计要点：工单号采用"BX + 日期 + 序号"规则，便于沟通与追溯；工单详情页的进度时间线由 RepairRecord 渲染，同时承担审计作用；为状态、提交时间、报修人、维修人字段建立索引，供统计查询使用。

## 八、系统边界声明

### 8.1 范围内

1. 三个角色的注册登录、身份认证与权限控制。
2. 报修工单的提交、查询、撤销、驳回、派单、改派、流转与归档。
3. 维修过程的进度更新与维修记录填写。
4. 报修现场照片与完工照片的上传、查看。
5. 维修结果的验收、退回与评分评价。
6. 报修分类、楼栋房间等基础数据维护。
7. 面向宿管的统计报表。

### 8.2 范围外

| 不实现的内容 | 原因 / 处理方式 |
| --- | --- |
| 对接学校统一身份认证（CAS、校园网账号） | 涉及校外系统权限，采用本地账号 + 学号唯一性校验模拟 |
| 短信、微信消息推送 | 涉及第三方付费通道，仅做站内页面提醒 |
| 备件库存管理与财务结算 | 属后勤仓储与财务范畴，维修材料仅做文字记录 |
| 与门禁、水电表等物联网设备对接 | 需要硬件支撑，超出软件课程项目范围 |
| AI 图像识别故障、智能派单算法 | 属算法方向，列为期末专项任务的扩展点 |
| 多校区、多学校（多租户）支持 | 系统定位为单校区内部系统 |
| 微信小程序端、原生 App | 采用响应式网页兼顾手机访问 |
| 支付与收费 | 报修服务不涉及收费 |

### 8.3 假设与约束

**假设**

1. 学生与维修人员的基础信息可由管理员导入或在后台创建。
2. 用户使用现代浏览器，通过校园网或移动网络访问系统。
3. 系统在单机环境下开发与验收，数据量为单校区规模。

**约束**

1. 必须使用 MySQL 作为数据库。
2. 项目由个人独立完成，不存在团队分工。
3. 开发周期为一个学期的课内实验学时。
4. 期末大作业需在此基础上完成 2～3 个专项任务，因此架构需预留扩展空间。
