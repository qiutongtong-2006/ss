# 学生宿舍报修管理系统 敏捷开发计划

个人独立开发　总工期 3～4 周　技术：Python 3.12 + Django 5.2 LTS + MySQL 8.0

## 一、敏捷在本项目怎么落地

个人项目没有团队，Scrum 的三个角色由我一人兼任（产品负责人、Scrum Master、开发人员），会议相应简化。三样工件必须保留：

- **产品待办列表**：全部用户故事按优先级排成一张表
- **迭代待办列表**：每个迭代开始时从列表顶部取故事，拆成任务
- **增量**：每个迭代结束都必须有一个能运行、能演示的功能

## 二、迭代安排（每个迭代 3～5 天，共 6 个）

| 迭代 | 天数 | 迭代目标 | 交付的增量 |
| --- | --- | --- | --- |
| 0 | 2 天 | 环境与清单就绪 | Django 项目骨架、MySQL 连接、用户故事清单 |
| 1 | 4 天 | 学生能登录并提交报修 | 登录页、报修提交页（含照片上传） |
| 2 | 4 天 | 宿管能受理并派单 | 工单池列表、受理/派单/驳回 |
| 3 | 4 天 | 维修人员能接单并记录 | 我的任务、维修记录、提交完工 |
| 4 | 3 天 | 学生能验收评价，闭环打通 | 验收与评分、工单详情时间线 |
| 5 | 4 天 | 权限加固与基础数据 | 三角色权限校验、用 Admin 维护分类与楼栋 |
| 6 | 3 天 | 缺陷修复与交付 | 测试、缺陷修复、文档与演示准备 |

工期紧，统计报表、超时提醒等功能放在待办列表末尾，做完 6 个迭代还有余力再补。

## 三、每个迭代内部的动作

1. **计划（半天）**：取故事 → 拆任务 → 估工时 → 写一句迭代目标
2. **执行（3～4 天）**：每天开工前自问三句——昨天做完了什么、今天做什么、遇到什么障碍
3. **测试**：每完成一个功能立即自测，让系统始终保持可运行
4. **评审（半小时）**：把增量跑一遍给自己或同学看，新想法写成用户故事放进待办列表
5. **回顾（15 分钟）**：写"保持、改进、尝试"各一条

## 四、一个迭代的示例（迭代 1）

**迭代目标**：学生能用学号登录，提交一条带照片的报修。

| 任务 | 工时 |
| --- | --- |
| Django 项目结构与 MySQL 配置 | 2h |
| 自定义用户模型（含角色字段）与迁移 | 2h |
| 注册、登录、退出页面 | 3h |
| 报修工单模型与工单号生成（BX+日期+序号） | 3h |
| 报修提交表单（含图片上传） | 4h |
| 按验收标准自测 | 2h |

合计 16 小时，约 4 天。每日站会记录：

| 天 | 昨天完成 | 今天计划 | 障碍与处理 |
| --- | --- | --- | --- |
| 1 | 项目骨架 | 用户模型、登录页 | mysqlclient 装不上，改用 PyMySQL |
| 2 | 用户模型、登录页 | 工单模型、工单号 | 无 |
| 3 | 工单模型 | 报修提交表单 | 图片路径混乱，改为按年月分目录 |
| 4 | 提交表单 | 自测与演示准备 | 无 |

**评审**：演示"登录 → 提交带照片的报修 → 后台看到工单"。反馈是希望提交后直接显示工单号，于是新增一条用户故事放进待办列表，**不打断当前迭代**。

**回顾**：保持——每天先写清当天三件事；改进——图片上传没写测试导致返工，下个迭代先写测试；尝试——下个迭代对工单状态流转先写测试。

## 五、需要留下的过程证据

实验报告附录放这些就够：用户故事清单、每个迭代的待办列表与任务板截图、每日站会记录、燃尽图、评审与回顾记录、每个迭代增量的系统截图。

## 六、三个提醒

不要在迭代最后一天才集成，否则系统长期不可运行；不要为了赶功能跳过测试，3～4 周的工期没有返工余量；迭代目标只写一句，做不完就把它拆小。

## 附录：用 MoSCoW 划分优先级

判定标准：**M** 缺了系统不能验收；**S** 很重要但短期可以降级；**C** 有更好；**W** 本次明确不做。

### M —— 必须有（Must have）

| 编号 | 用户故事 | 完成迭代 |
| --- | --- | --- |
| M1 | 学生用学号与密码登录系统 | 1 |
| M2 | 学生提交报修（楼栋房间、分类、描述、照片） | 1 |
| M3 | 宿管查看工单池并受理派单 | 2 |
| M4 | 维修人员查看任务并接单 | 3 |
| M5 | 维修人员填写维修记录并提交完工 | 3 |
| M6 | 学生验收并给出结果 | 4 |
| M7 | 工单状态按规则流转，可查看详情 | 2～4 |
| M8 | 三角色权限控制（学生只看自己的、维修工只看分派的） | 随功能同步 |

### S —— 应该有（Should have）

| 编号 | 用户故事 | 完成迭代 |
| --- | --- | --- |
| S1 | 学生在受理前撤销报修 | 2 |
| S2 | 宿管驳回工单并填写原因 | 2 |
| S3 | 工单详情展示完整处理时间线 | 4 |
| S4 | 学生对维修结果评分并写评价 | 4 |
| S5 | 工单按状态、分类、楼栋筛选 | 2 |
| S6 | 楼栋与报修分类的维护（用 Django Admin） | 5 |

### C —— 可以有（Could have）

| 编号 | 用户故事 | 处理方式 |
| --- | --- | --- |
| C1 | 报修统计报表（总量、分类占比、完成率） | 迭代 6 有余力再做 |
| C2 | 超时未受理提醒 | 迭代 6 有余力再做 |
| C3 | 个人信息维护与修改密码 | 迭代 6 有余力再做 |
| C4 | 完工照片上传 | 已取消，不纳入本次交付 |
| C5 | 统计结果导出为表格 | 不排入迭代 |

### W —— 本次不做（Won't have）

对接学校统一身份认证、短信与微信推送、备件库存与财务结算、智能派单与图像识别、多校区多租户、微信小程序与原生 App、在线支付收费。

### 使用规则

1. **M 类工作量控制在总工作量的 60% 左右**，S 类约 25%，C 类约 15%。如果 M 类超过七成，说明范围没有收敛。
2. 优先级不等于开发顺序。S 类中成本低的（如筛选）可以提前做，C 类中成本高的（如报表）往后放。
3. W 类要写进报告的"系统边界声明"，这是你答辩时解释"为什么没做这些功能"的依据。
4. 迭代中不排 C 类任务，把它们当作缓冲：提前完成迭代目标后才从 C 类里取。
