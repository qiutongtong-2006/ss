## 2 可行性研究的前提

### 2.1 要求

**功能要求**

1. 用户管理：注册、登录、个人信息维护，按三种角色区分权限。
2. 报修管理：学生提交报修（含现场照片）、查看进度、撤销、验收评价。
3. 维修处理：维修人员查看任务、接单、填写维修记录、提交完工。
4. 管理端：宿管受理与驳回、派单与改派、工单查询、基础数据维护。

**性能要求**：支持约 100 人同时在线；列表分页显示；普通页面响应时间不超过 3 秒。

**接口要求**：用户通过浏览器（含手机浏览器）访问，不要求与其他系统对接。

**约束**：必须使用 MySQL 数据库；开发周期 3～4 周；由个人独立完成。

### 2.2 目标

1. 把宿舍报修流程由线下转移到线上，缩短从报修到受理的响应时间。
2. 让学生能随时查询报修进度，减少重复报修和电话催问。
3. 沉淀完整的报修与维修数据，为后勤部门统计故障分布、维修工作量提供依据。

### 2.3 条件、假定和限制

**条件**：个人电脑一台，Python、Django、MySQL 均为开源软件，可免费获取。

**假定**

1. 学生、宿管和维修人员均能使用手机或电脑访问网页。
2. 校园网覆盖学生宿舍与后勤办公区域，网络正常。
3. 宿管与维修人员愿意按系统流程录入与更新信息。
4. 报修数据量为单校区规模，年均约 6000 条工单。

**限制**

1. 开发周期为 3～4 周，功能必须裁剪，优先保证主流程。
2. 只有一名开发者，不能并行推进多个模块。
3. 不对接学校统一身份认证、短信或微信推送等外部系统。
4. 演示与运行环境为单机部署。

### 2.4 决定可行性的主要因素

1. 技术因素：Django 能否在有限时间内实现三角色权限与工单状态流转。
2. 经济因素：项目几乎不产生直接支出，只需论证人力成本是否值得投入。
3. 操作因素：宿管与维修人员是否愿意放弃纸质登记，改用系统处理。
4. 进度因素：3～4 周内能否交付一个完整可演示的闭环。

## 3 对现有系统的分析

### 3.1 处理流程和数据流程

**现有处理流程**

学生发现设施损坏 → 口头告知宿管、打电话或发到楼栋微信群 → 宿管在纸质登记本上记录 → 宿管电话通知维修人员 → 维修人员上门维修 → 口头回复宿管或学生 → 学生自行确认是否修好

**现有数据流程**

报修信息（口述或聊天记录）→ 纸质登记本 → 登记本长期保存但难以检索 → 无任何统计汇总

整个过程中，报修信息只在"人的记忆"和"纸质本子"里流转，没有结构化的数据载体。

### 3.2 工作负荷

按单校区 3000 名住宿学生估算，年均报修约 6000 条，日均约 20 条。宿管每处理一条报修，登记与转达约需 3～5 分钟，平均每天约 1～1.5 小时用于报修事务；维修人员则需多次电话确认位置与故障情况。

### 3.3 费用支出

现有方式几乎没有直接费用支出，主要成本是宿管与维修人员的时间成本，按每年约 250 小时折算，人力成本约 5000 元/年。

### 3.4 人员

宿管 2～3 人，负责登记、转达与跟进；维修人员 5～8 人，按水电、木工、网络等工种分工；没有专职的信息系统管理人员。

### 3.5 设备

现有设备为办公电脑、手机、打印机和纸质登记本。缺少服务器与数据库运行环境，但本项目可采用单机部署，使用现有电脑即可。

### 3.6 局限性

1. 报修信息零散、无统一记录，容易出现漏记、漏单。
2. 学生提交报修后得不到回执，无法查询进度，只能反复催问。
3. 同一故障被多人重复报修，维修人员重复上门。
4. 无法统计故障分类分布、楼栋故障排行、平均处理时长与人员工作量。
5. 处理过程与结果无法追溯，出现争议时缺少依据。
6. 纸质记录难以检索、难以长期保存，也无法支撑数据分析。

## 4 所建议系统的可行性研究

### 4.1 对所建议系统的简要描述

拟开发的学生宿舍报修管理系统是一个基于浏览器的信息管理系统，设置学生、维修人员、宿管/管理员三种角色。学生在线提交报修并上传现场照片，宿管集中受理并派单，维修人员接单并记录维修过程，最后由学生验收评价，形成"报修—派单—维修—验收—归档"的线上闭环，所有数据保存于 MySQL 数据库中。

系统采用 Python + Django + MySQL 开发，使用 Django 模板与 Bootstrap 服务端渲染，单机部署；基础数据（楼栋、报修分类）的维护直接复用 Django 自带的后台管理功能，以减少开发量。

### 4.2 处理流程和数据流程

**新系统的处理流程**

1. 学生登录后填写楼栋、房间号、报修分类、故障描述、紧急程度并上传照片，提交后生成工单，状态为"待受理"。
2. 宿管在工单池中查看工单，受理并指派维修人员，状态变为"已派单"；如属重复报修或非职责范围，填写原因后驳回。
3. 维修人员接单，状态变为"维修中"；维修完成后填写维修记录并提交完工，状态变为"待验收"。
4. 学生验收：确认已修复则评分评价，状态变为"已完成"；未修复则填写原因，工单退回重新派单。
5. 工单归档，数据进入统计查询范围。

**新系统的数据流程**

浏览器表单 → Django 视图（业务规则与状态校验）→ MySQL 数据表 → 各角色查询页面

数据库共设计 8 张业务表：用户表、楼栋表、报修分类表、报修工单表、工单图片表、维修过程记录表、验收评价表、操作日志表。其中报修工单表是核心，存储工单号、报修人、维修人、状态与各节点时间；维修过程记录表保存完整的处理轨迹，支撑工单详情页的时间线展示与事后追溯。

### 4.3 与现有系统比较的优越性

1. 报修信息结构化存储，不再依赖记忆和纸质本子，不会漏记。
2. 提交即有回执与工单号，学生可随时查询进度，减少催问。
3. 同一房间同一分类的未完成工单会有重复提示，减少重复上门。
4. 处理过程完整留痕，责任清晰，出现争议时有据可查。
5. 报修量、分类占比、完成率、人员工作量可自动统计，为后勤管理提供数据支持。
6. 无纸化记录，长期保存成本更低。

### 4.4 采用建议系统可能带来的影响

1. 宿管与维修人员需要适应新的工作方式，预计需要半天培训。
2. 需要有人承担系统日常维护（如账号管理、数据备份），可由宿管兼任。
3. 过渡期内，原有的纸质登记方式建议保留，待系统稳定运行后再取消。
4. 学生需要改变"在群里喊一声"的习惯，可通过楼栋公告引导使用。

### 4.5 技术可行性评价

**技术发展**：Python + Django + MySQL 是目前非常成熟的技术组合，Django 自带 ORM、用户认证与后台管理，能够显著减少基础代码量，网上文档与案例丰富，遇到问题容易找到解决方案。

**资源供给**：开发者已在课程中学习 Python 编程与数据库基础知识，具备完成本项目的技能前提；开发只需一台个人电脑，所用软件全部开源免费；不需要专门的服务器，单机即可完成开发与演示。

**开发风险**：主要风险在于工单状态流转的逻辑（七个状态之间的合法性校验）和三角色的权限控制。应对措施是把状态流转集中写在视图层统一校验、禁止页面直接修改状态字段，并针对状态流转和越权访问编写测试用例；图片上传、列表分页等属于常规实现，风险较低。

**结论**：现有技术完全能够实现所定义的系统，技术上是可行的。

### 4.6 经济可行性评价

**支出（开发与运行成本）**

| 项目 | 金额 | 说明 |
| --- | --- | --- |
| 硬件设备 | 0 元 | 使用现有个人电脑，不需要采购服务器 |
| 软件费用 | 0 元 | Python、Django、MySQL 全部开源免费 |
| 培训费及资料费 | 约 100 元 | 参考资料打印等 |
| 合计 | 约 100 元 | 直接支出极低 |

**效益（新系统带来的收益）**

1. 节省的运行费用：宿管登记与转达、维修人员电话确认的时间预计每年节省约 200 小时，按 20 元/小时折算约 4000 元/年。
2. 减少重复上门与返工：重复报修提示可减少无效出工，预计每年节省约 1000 元。
3. 隐性收益：报修数据可统计，为后勤资源配置提供依据；学生满意度提升。

**收益/投资比**：投入约 100 元，年化效益约 5000 元，收益远大于投资。由于本项目为课程项目，开发人力不计入成本，实际投资回收期为一个月以内。

**敏感性分析**：即使效益估算偏乐观、实际只实现一半（约 2500 元/年），仍远高于 100 元的投入，结论对效益估算不敏感，风险很小。

**结论**：经济上是可行的。

### 4.7 操作可行性评价

**组织因素**：后勤管理处有规范报修流程、提高服务响应速度的现实需求，宿管与维修人员是直接受益方，具备推动系统使用的组织基础。

**法律因素**：系统仅采集姓名、学号、宿舍房间号与联系方式等办理报修业务必需的信息，不涉及信息的对外提供与商业使用，符合学校的规章制度和相关法律法规要求；系统中的报修照片仅用于维修业务，访问范围受角色权限限制。

**用户使用**：系统界面为浏览器网页，采用响应式布局，学生可直接用手机报修；学生端操作只有"提交报修""查看进度""验收评价"三个主要入口，宿管端与维修人员端的操作也集中在列表与表单，经过半小时的操作说明即可上手。因此系统在运行和使用上是可行的。

## 5 其他可供选择的方案

**方案一：微信小程序 + 云开发**

优点是学生使用最方便，无需输入网址；缺点是需要在 3～4 周内同时完成小程序端、云函数与数据库设计，还涉及小程序账号注册与上线审核，个人独立开发的进度风险较高。

**方案二：在线问卷或共享表格收集 + 人工派单**

优点是几乎不需要开发，成本最低；缺点是没有状态流转、没有进度反馈、没有权限控制，问题的本质（信息不结构化、过程不可见、数据不可统计）依然存在，只能算临时缓解措施。

**方案三：采购现成的商业报修 SaaS 服务**

优点是功能完善、上线快；缺点是需要持续支付服务费，数据存放在第三方，且与软件工程课程"完成需求分析、设计、编码、测试全过程"的目标不符。

**方案四（建议采用）：自行开发基于 Django 的 Web 系统**

优点是技术成熟、成本极低、功能可裁剪、完全可控，开发过程正好覆盖课程要求的各个阶段；缺点是需要投入 3～4 周开发时间，界面美观度不如商业系统。

综合比较，方案四在成本、进度和课程目标之间最为平衡，推荐采用。

## 6 结论

经从技术、经济、操作三个方面分析：本系统所采用的技术成熟、开发资源具备、直接成本仅约 100 元、使用方式简单，且现有报修方式确实存在信息零散、进度不可见、数据无法统计等问题，系统建成后能带来明显的效率提升。

主要风险集中在两个方面：一是 3～4 周的工期偏紧，二是工单状态流转与三角色权限的实现。前者通过裁剪功能（保留主闭环、基础数据维护交给 Django 后台、暂不做统计报表）控制，后者通过集中校验与测试用例控制，风险均可接受。

**结论意见：建议立即启动开发。** 开发中优先保证"报修—派单—维修—验收"主流程的完整与可用，再视剩余时间补充统计查询等功能；同时建议用户单位指定一名宿管兼任系统联系人，负责验收前的试用与反馈。
